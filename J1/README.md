# J1. Сервер генерации ключей

Программа состоит из TCP-сервера и клиента. Клиент отправляет имя, сервер создаёт для него пару RSA-ключей на 8192 бит и сертификат X.509. Если такое имя уже встречалось, сервер возвращает сохранённые ключ и сертификат

Используются Java 21, Gradle, Bouncy Castle 1.80 и JUnit 5.11.4

## Реализация

Сетевые соединения обслуживаются одним потоком через `Selector`. Этот поток принимает подключения, читает имена и отправляет ответы. Отдельный поток ОС для каждого клиента не создаётся

Генерация ключей выполняется в фиксированном пуле. Число потоков передаётся при запуске сервера. Задачи ожидают свободного потока во внутренней очереди пула

Для каждого имени в кэше хранится `CompletableFuture` с результатом генерации. Он добавляется до отправки задачи в пул. Повторный запрос получает тот же объект и ждёт готовый ключ, новая задача для него не создаётся

После генерации ответ помещается в очередь готовых результатов. Сетевой поток забирает его и отправляет клиенту. Если за одну неблокирующую запись отправлена только часть ответа, оставшаяся часть остаётся в `ByteBuffer` до следующего события записи. Медленный клиент не удерживает поток генерации

Имя клиента записывается в поле `CN` субъекта сертификата. Имя издателя задаётся при запуске сервера. Сертификат подписывается заранее созданным ключом издателя, который сервер читает из файла. Публичный ключ клиента находится внутри сертификата

## Запуск в IntelliJ IDEA

Открыть папку `J1` как Gradle-проект и выбрать Java 21. Все классы находятся в пакете `ru.nsu.vorona`. Рабочая папка конфигураций запуска — папка `J1`

1. Один раз запустить `SignerMain` с аргументом:

   ```text
   signing.key
   ```

   Будет создан ключ подписи на 3072 бита. Это отдельный ключ издателя; клиентские ключи сервер создаёт на 8192 бит. Файл `signing.key` нужно оставить для следующих запусков. Если он уже существует, повторно запускать генератор не нужно

2. Запустить `ServerMain` с аргументами:

   ```text
   9000 4 signing.key TestIssuer
   ```

   Порядок: порт, число генерирующих потоков, путь к ключу подписи, имя издателя. Сервер слушает на всех IPv4-интерфейсах

3. Не останавливая сервер, запустить `ClientMain` с аргументами:

   ```text
   127.0.0.1 9000 IvanIvanov
   ```

   Клиент сохранит `IvanIvanov.key` и `IvanIvanov.crt` в своей рабочей папке. Для подключения с другого компьютера вместо `127.0.0.1` нужно указать IP-адрес или DNS-имя сервера и разрешить входящие подключения к выбранному порту

Дополнительные аргументы клиента:

| Аргумент | Что делает |
| --- | --- |
| `--delay=5` | После отправки запроса ждёт 5 секунд перед чтением ответа |
| `--abort` | Отправляет запрос и закрывает соединение без чтения ответа |
| `--out=results` | Сохраняет файлы в папку `results` |

Например, медленный клиент:

```text
127.0.0.1 9000 IvanIvanov --delay=5 --out=results
```

Тайм-аут подключения составляет 5 секунд. Время ожидания ответа не ограничено, поскольку оно зависит от длительности генерации и количества запросов в очереди

## Формат обмена

Запрос — имя в ASCII и нулевой байт в конце. В реализации разрешены от 1 до 128 печатных ASCII-символов

Ответ начинается с байта статуса:

| Значение | Результат |
| --- | --- |
| `0` | Успех |
| `1` | Неверный запрос |
| `2` | Ошибка генерации |

При успехе передаются длина приватного ключа, ключ в PEM, длина сертификата и сертификат в PEM. Длины занимают по 4 байта в порядке big-endian. При ошибке передаются длина сообщения и сообщение в UTF-8. Клиент не принимает отдельный блок размером больше 1 МиБ

## Тестирование

Запуск из папки `J1`:

```text
gradle test
```

Восемь тестов проверяют сертификат и соответствие ключей, повторные и разные имена, неверный запрос, отключение клиента и остановку сервера

Для проверки одновременной работы создаются 100 клиентов с одним именем. Каждый пятый клиент задерживает чтение на одну секунду. Проверяется, что все клиенты получают один и тот же ключ

В тестах используются RSA-ключи на 2048 бит для сокращения времени выполнения. При обычном запуске сервер генерирует ключи на 8192 бит

## Ограничения

Кэш находится только в оперативной памяти. После перезапуска сервера для того же имени будут созданы новые ключи. Ограничение количества имён и очистка старых записей не реализованы

При сохранении файлов символы имени, кроме латинских букв, цифр, `_` и `-`, заменяются на `_`. Поэтому разные исходные имена могут дать одинаковое имя файла. Уже существующие файлы перезаписываются; для отдельных проверок можно указывать разные папки через `--out`

Передача приватных ключей по обычному TCP реализована по условию задания и не подходит для реального использования
